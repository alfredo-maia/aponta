# Módulo: Relatórios & Apontamentos (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implementar o motor de relatórios analíticos, focando primariamente em Faturamento e Carga de Trabalho (Atendentes). Para entregarmos um sistema "melhor que o Tiflux", primeiramente criaremos a fundação real de *Apontamento de Horas* (Worklogs) conectada à trilha de segurança do Tenant.
**Architecture:** 
- Inserir a entidade `Worklog` atrelada ao `Ticket` e ao `User` (Agent).
- O `ReportsController` centralizará endpoints paramétricos (ex: `GET /reports/workload`, `GET /reports/billing`), mapeando a carga pelo DB através das clauses robustas do `TenantHelper`.
- O Frontend gerará gráficos ou extratos agregados divididos nas famosas painéis (Accordion): *Atendentes, Faturamento e Administrativo*.
**Tech Stack:** NestJS, Prisma, OpenAPI (MCP-Ready), React, React Query (possibilidade de usar Recharts p/ grafos no futuro, mas MVP é textual/lista agregada).
**Spec:** `docs/superpowers/specs/2026-10-02-aponta-evolution-design.md`

## Global Constraints
- **Segurança Analítica Ocular:** Nenhum Agent pode solicitar o endpoint de `/reports/billing`. Ele deve falhar com Forbidden (403). Agentes só têm autorização no `/reports/workload`.
- **Tenant Rigidity em Extratos:** Quando o `CLIENT_MASTER` acessar relatórios, todas as Queries Prisma por baixo DEVEM espalhar via `TenantHelper.getTicketWhere(user)` para assegurar que apenas dados dos tickets de sua `organizationId` componham o agrupamento final do relatório matemático.

## Review Focus
- **Spoofing de Dados Transversais:** Um Agent não pode injetar o user ID de um colega na rota `/reports/workload?agentId=x` para bisbilhotar a métrica alheia. A API intercepta explicitamente e injeta o `currentUser.id` caso o rank seja `AGENT`. Apenas `ADMIN` / `AGENT_MASTER` podem brincar com o query param `agentId`.
- **Tipagem Aberta (Any):** O controller devolverá respostas complexas com `.groupBy()`. O DTO de resposta do Swagger (MCP) deve ser tipado rigidamente com `class-validator/transformer`, pois a IA não consegue interpretar um "JSON solto" da forma mágica que o Prisma expele.

### Task 1: Prisma Schema para Apontamentos (`Worklog`)

**Files:**
- Modify: `apps/api/prisma/schema.prisma`

**Interfaces:**
- Produces: `Worklog` entity (representing "Apontamento" em pt-BR).

- [ ] **Step 1: Injetar Worklog (Apontamento)**
Modificar o schema adicionando a base para contabilização financeira e de produtividade:
```prisma
model Worklog {
  id          String   @id @default(uuid())
  description String
  minutes     Int      // Tempo apontado
  billable    Boolean  @default(true)
  ticketId    String
  ticket      Ticket   @relation(fields: [ticketId], references: [id])
  authorId    String
  author      User     @relation(fields: [authorId], references: [id])
  createdAt   DateTime @default(now())
}
```
*(Não se esquecer de puxar o lado da relação pra `Ticket` e `User` como `worklogs Worklog[]`)*

- [ ] **Step 2: Gerar DB Diff & Prisma Client**
Run: `npx prisma migrate dev --name add_worklogs_table` e `api:prisma-generate`.
