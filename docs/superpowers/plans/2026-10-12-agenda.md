# Módulo de Agenda (Appointments & Alocação Temporal) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implementar o módulo de Agenda de compromissos, alocações e ausências da equipe técnica com controle rigoroso de RBAC e isolamento multi-tenant, atendendo à Seção 3.7 do SDD de Evolução e à Issue GitHub #46 (Multica DMTE-18).
**Architecture:**
- **Data Layer:** Modelo Prisma `Appointment` associado a `User`, opcionalmente associado a `Organization` e `Ticket`. Enum `AppointmentType` (`APPOINTMENT`, `ABSENCE`, `ALLOCATION`).
- **Backend API (NestJS):** Módulo `AgendaModule` com DTOs tipados e validados (`class-validator`, `@ApiProperty` para MCP-Readiness), centralização de isolamento via `TenantHelper.getAppointmentWhere`, controller com guards de papel (`@Roles`).
- **Frontend SPA (React):** Rota `/schedule` ativada no `Sidebar.tsx` e `App.tsx`, tela `SchedulePage.tsx` utilizando componentes nativos do Design System (`apps/web/src/components/ds/`), suporte à visualização temporal (mês/semana/dia), filtro de atendentes para Admin/Agent Master, e modal de criação/edição de compromissos.
**Tech Stack:** NestJS, Prisma ORM, PostgreSQL, React, TanStack Query, TailwindCSS v4, Lucide Icons.
**Spec Reference:** `docs/superpowers/specs/2026-10-02-aponta-evolution-design.md` (seção 3.7) & GitHub Issue #46.

---

## Global Constraints & Security Posture (RBAC)
- **ADMIN:** Controle multi-agent irrestrito, visão global da equipe, filtragem por usuário e tipo, permissão para criar, editar e excluir qualquer compromisso/alocação.
- **AGENT_MASTER:** Visão dos técnicos vinculados às suas Mesas de Serviço (`ServiceDesk`) e dos seus próprios agendamentos; inserção e edição dos seus blocos.
- **AGENT:** Calendário focado estritamente no seu próprio contexto (`userId === currentUser.id`); criação e edição exclusivas dos seus próprios blocos temporais.
- **CLIENT_MASTER:** Visão filtrada pelo seu `organizationId` (somente compromissos diretamente vinculados à sua empresa). **Regra Crítica:** Ausências internas da equipe técnica (`ABSENCE` - férias, folgas, licenças) são estritamente filtradas/mascaradas na query do backend para não expor a equipe ao cliente.
- **CLIENT:** Bloqueio total (HTTP 403 Forbidden). Rota e menu permanecem 100% ocultos.
- **Datas:** Validação obrigatória garantindo que `endTime` seja posterior a `startTime`.
- **Relação com Worklog (#44):** `Appointment` trata do agendamento temporal (futuro/presente/planejamento). Os apontamentos de horas realizados (`Worklog`) poderão ser consumidos na visão do Admin como histórico de horas executadas.

---

## Review Focus
- **Tenant & RBAC Leakage:** Um `CLIENT_MASTER` chamando `GET /appointments` jamais deve receber eventos do tipo `ABSENCE` ou eventos de outras organizações. Um `AGENT` não pode editar agendamentos de outros agentes a menos que seja `ADMIN`.
- **Validação de DTOs:** Rejeição de intervalos inválidos (`endTime <= startTime`) no nível de DTO e Service.
- **Design System Fidelity:** Uso dos componentes DS do Aponta (`EzButton`, `EzTextInput`, `EzTabs`, `EzBadge`) sem dependências externas incompatíveis.

- [ ] **Step 1: Extender TenantHelper**
Adicionar `TenantHelper.getAppointmentWhere(user: CurrentUserPayload): Prisma.AppointmentWhereInput`:
- `ADMIN`: Retorna `{}` (sem restrição).
- `CLIENT_MASTER`: Retorna `{ organizationId: user.organizationId, type: { not: AppointmentType.ABSENCE } }`.
- `AGENT`: Retorna `{ userId: user.id }`.
- `AGENT_MASTER`: Retorna `{ OR: [{ userId: user.id }, { user: { serviceDesks: { some: { agents: { some: { id: user.id } } } } } }] }` ou `{ userId: user.id }`.
- `CLIENT`: Fail closed `{ id: '00000000-0000-0000-0000-000000000000' }`.

- [ ] **Step 2: Criar DTOs com validação estrita (MCP-Ready)**
Anotar campos com decorators `class-validator` (`@IsString()`, `@IsNotEmpty()`, `@IsDateString()`, `@IsEnum()`, `@IsOptional()`) e `@ApiProperty()`.
Adicionar validação customizada ou no service para `endTime > startTime`.

- [ ] **Step 3: Implementar AgendaService com TDD**
Métodos:
- `findAll(query: QueryAppointmentDto, user: CurrentUserPayload)`: Combina filtros da query (`startTime`, `endTime`, `userId`, `type`) com a restrição do `TenantHelper`.
- `findOne(id: string, user: CurrentUserPayload)`: Verifica permissão de acesso.
- `create(dto: CreateAppointmentDto, user: CurrentUserPayload)`: Injeta `userId` do próprio usuário se for `AGENT`; permite atribuir outro usuário apenas para `ADMIN`/`AGENT_MASTER`.
- `update(id: string, dto: UpdateAppointmentDto, user: CurrentUserPayload)`: Garante que apenas o autor ou `ADMIN` possa editar.
- `remove(id: string, user: CurrentUserPayload)`: Exclusão permitida para autor ou `ADMIN`.

- [ ] **Step 4: Criar AgendaController com Guards de Papel**
- `@UseGuards(JwtAuthGuard, RolesGuard)`
- `@Get()` -> `@Roles(Role.ADMIN, Role.AGENT_MASTER, Role.AGENT, Role.CLIENT_MASTER)`
- `@Post()`, `@Patch(':id')`, `@Delete(':id')` -> `@Roles(Role.ADMIN, Role.AGENT_MASTER, Role.AGENT)`
- Testes unitários com mock do Prisma e verificação rigorosa de 403 e payloads filtrados.
